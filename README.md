# NTLRAG - Narrative Topic Labels derived with Retrieval Augmented Generation

NTLRAG is a modular narrative labeling framework that generates semantically precise and human-interpretable topic labels while minimizing human effort. NTLRAG uses standard topic model outputs to generate, validate, and refine narratives that serve as topic labels.
The orchestrated RAG framework uses multiple retrieval strategies and chain-of-thought elements to provide high-quality output.

It extracts narratives from document clusters using the following structure:

1. one or more actor(s),
2. an action associated with the actor(s), and
3. an event linking these components.
   
To improve interpretability, we additionally include a concise descriptive text that connects these three elements. This structure is further used as a narrative schema for topic labels extracted and generated by NTLRAG. Our framework allows the implementation of various models and technologies for its four components (RETRIEVER, EXTRACTOR, VALIDATOR and REFINER), which are presented with the corresponding workflow in the graph below.

## Demo implementation
In this repository we provide a demo implementation of NTLRAG using LangChain, LangGraph, Ollama (llama3.2) and Pydantic. To replicate our results, we provide the following four files:

1. `testdata_cleaned.csv`, which is the input file for the topic model,
2. `testdata_seedtopics.csv`, which equals the output of topic modeling,
3. `testdata_topic_keywords.json`, which includes representative keywords for each topic (as provided by the topic model), and
4. `testdata_news.json`, which consists of news content used for validation and obtained via GNews package. 

### Input data for topic modeling
Input data for NTLRAG is typically (but not restricted to) the output of a topic model. Any model that provides: 

1. a deterministic topic assignment for each document,
2. the full (cleaned) text of each document and
3. a set of representative keywords per topic

can be used for the required upstream task.

For our demo, we opt for BERTopic (https://github.com/MaartenGr/BERTopic/tree/master, https://arxiv.org/abs/2203.05794), a modular topic model that uses transformer-based embeddings and clustering algorithms for topic detection.
As input data for topic modeling, we use a subsample (1,000 posts) of this X dataset on the U.S. election in 2024 (https://github.com/sinking8/x-24-us-election, see https://arxiv.org/abs/2411.00376 for the corresponding publication) to showcase basic functionality. Text Pre-processing steps for our subsample included: Hashtag transformation (e.g. #VoteForKamala into Vote For Kamala),  @-mention and URL substitution with @USER and HTTPURL respectively and removal of Emojis. The resulting file testdata_cleaned.csv consists of the following columns and datatypes. 

**testdata_cleaned.csv** includes the following information (slightly adjusted to the source data set):

| retweetCount     | quoteCount    | replyCount     | retweetedTweet             | date              | user                      | text                       | lang                  | likeCount                       | id                               | cleaned_text                     |
|------------------|---------------|----------------|----------------------------|-------------------|---------------------------|----------------------------|-----------------------|---------------------------------|----------------------------------|----------------------------------|
| no. of retweets  | no. of quotes | no. of replies | is this a retweeted tweet? | date of the tweet | user information/metadata | original text of the tweet | language of the tweet | no. of likes the tweet received | unique identifier for each tweet | cleaned version of original text |

Hyperparameters for BERTopic were tuned using OPTUNA (https://github.com/optuna/optuna).

### Input data for NTLRAG

NTLRAG requires three input documents:

| File | Format | Description of minimal content                                                                                                   | Filename in demo             |
|------|--------|----------------------------------------------------------------------------------------------------------------------------------|------------------------------|
| 1    | csv    | a row for each document and the columns 'Document' (text of each document) and 'Topic' (topic number assigned to each document). | `testdata_seedtopics.csv`      |
| 2    | json   | representative keywords for each topic with topic key assigned                                                                   | `testdata_topic_keywords.json` |
| 3    | json   | news data                                                                                                                        | `testdata_news.json`           |                                                                                                                         

To obtain news data for our demo, we used the GNews package for Python (https://github.com/ranahaani/GNews).

### Setup 

The following components include models that can be adjusted/selected by the user:

- **RETRIEVER**: Chroma and BM_25 retrievers, embeddings via llama3.2 via ollama, number of retrieved documents
- **EXTRACTOR**: LLM (llama3.2 locally via ollama)
- **VALIDATOR**: LLM (llama3.2 locally via ollama), maximum number of refines, recursion limit
- **REFINER**:   LLM (llama3.2 locally via ollama)

If all components should remain unchanged, the `setup.ps1` file for windows and the `setup.sh` file for Linux will install required packages (see `requirements.txt`).

To use local LLM models for Extractor/Validator/Refiner components, install [Ollama](https://ollama.com/download) for your system

After setting up your preferred LLM or any other EXTRACTOR, consult `settings.py` and adjust parameters according to your choice.

The following models are not included in the `settings.py` and need to be adjusted in `demo.py` (see comments): LLM, retrievers, embedding model.

## Output 

After either adjusting parameters as described above or just running the `demo.py` file as is, NTLRAG prints the processing history for each topic and saves multiple output files.

In the output directory NTLRAG saves one file for each topic with all retrieved documents (from short texts and news) and the approved narrative and one .json file for all topics with all approved narratives for each topic (`approved_narratives_global.json`). Results of our demo implementation are provided in [results](data/results).

To learn more about NTLRAG and its functionality consult the corresponding preprint on arXiv (https://arxiv.org/abs/2602.17216).
